## 二、一句话架构

```
浏览器 (Vue3 + Element Plus)
    │  HTTP/JSON (REST + SSE 进度推送)
    ▼
FastAPI 后端 (Python 3.11, conda env: catong_gen)
    ├── 提示词管理模块（库/模板/片段/预设/变量）★ 地基
    ├── 提示词拼装引擎（分段渲染管线）★ 地基
    ├── 业务模块：小说中心 → 角色中心 → 项目/分镜 → 生成调度 → 导出
    ├── LLM 供应商适配层（DeepSeek / 火山 / OpenAI 兼容...）
    └── 图像/视频供应商适配层（即梦/GRSai/nano-banana 兼容...）
    │
    ▼
SQLite (SQLAlchemy 2.x + Alembic 迁移)  +  文件系统 (Output/ roles/ 画风库/)
```

## 三、两个"地基"模块为什么最先做

雪漫画的每一个 AI 能力（角色提取、文案改写、分镜拆分、图片提示词推导、视频提示词、小说评分）本质上都是同一件事：

```
【某业务阶段】= 【一段提示词指令】 × 【组装好的上下文】 × 【某个 LLM/图像模型】
```

因此本项目的实施顺序是：**先把"提示词管理"和"提示词拼装"这两个地基模块做出来（Phase 1），再逐段接入业务流程**。这样后期每接一个业务阶段，只需：

1. 在提示词库里选/写一条该阶段的指令模板；
2. 在拼装引擎里声明该阶段的上下文分段（变量从哪来）；
3. 业务代码只负责收集上下文、调用引擎、把结果落库。

这正是"便于后期拆解提示词拼装"的落点：**提示词与业务代码彻底解耦**。
